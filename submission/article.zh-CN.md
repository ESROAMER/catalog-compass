# Catalog Compass 用本地 AI 帮助自由职业者检查供应商商品表

*本文是 [Hacktoberfest 开源 AI 挑战赛第二周 Side Hustle](https://dev.to/challenges/hacktoberfest-week2-2026-10-12) 的参赛文章草稿。*

## 我做了什么（What I Built）

供应商发来一张商品表，列名分别是 `Item ref`、`Display label`、`List amount` 和 `GTIN`。在导入店铺之前，需要有人弄清这些列分别代表什么，找出缺失的价格，并确认为什么同一个商品编号会对应两个不同的价格。

Catalog Compass 就是为这一步检查准备的小工具。开放权重模型先建议每一列对应哪个字段，由人确认，再用 Python 规则找出缺失价格、重复的商品编号（SKU）和冲突记录，同时列出相关行及原始值。

它面向帮助网店整理供应商文件的自由职业者，也适合自己处理这些工作的商家。输出很具体：一份便于和供应商沟通的 CSV 问题报告，以及一份完成字段映射、供后续导入流程使用的 CSV。原始文件保持不变。

公开的自由职业招聘需求帮助我确定了这个使用场景。完整的商品导入工作可能涉及商品变体、图片、翻译和不同店铺的更新要求。Catalog Compass 聚焦于检查单份供应商 CSV，并整理检查结果，供后续工作使用。

自由职业者可以据此提供一项范围明确的服务：检查单份供应商文件，处理异常，并交付检查后的文件。

## 演示（Demo）

[观看或下载带解说的演示视频（MP4）](https://github.com/ESROAMER/catalog-compass/blob/master/submission/video/catalog-compass-demo.mp4)。

视频使用真实应用界面截图和实际的本地模型推理结果，经过讲解剪辑，并配有合成的英文旁白。演示中的供应商文件包含 10 条虚构商品记录，已随项目提供。

你可以按下面的步骤重现操作：

1. 打开应用，点击 **Load sample with errors**，载入带错误的样例。
2. 点击 **Suggest with AI**，对照每列旁边的示例值，检查 AI 建议的字段对应关系。
3. 确认 `Item ref` 对应 SKU，`Display label` 对应商品名称，`List amount` 对应正常售价。在可选字段中，`GTIN` 对应条码，`Kind` 对应商品类型。原表没有提供的字段保持未选择。
4. 勾选已检查字段选择的确认项，再点击 **Check for issues**。
5. 查看检查结果：**4 个错误、6 个警告，涉及 10 行中的 9 行**。然后下载问题报告或完成字段映射的 CSV。

## 代码（Code）

[源代码和安装说明](https://github.com/ESROAMER/catalog-compass)。

我在本次比赛期间的 2026 年 10 月 15 日开始创建这个仓库。应用代码和虚构演示数据采用 MIT 许可证。公开的 WooCommerce 和 CrossPeak 样例保留各自的许可证，仓库中也记录了源文件的哈希值。

网页应用需要 Python 3.11 或更高版本，以及一个浏览器，不需要通过 pip 或 npm 安装依赖。在 Windows 上，可以双击 **Start Catalog Compass.cmd**，也可以运行：

```powershell
python app.py --open
```

在 **AI settings** 中，本地模式提供安装和启动按钮。首次在 Windows x64 上安装时，会下载约 672 MB 的模型和运行文件；以后启动时会复用这些文件。如果 GPU 启动失败，也可以选择 CPU 模式。

应用还提供可选的 API 模式，接受兼容 Chat Completions 的服务地址、模型 ID 和密钥，使用这种方式不需要下载本地模型。本次比赛演示使用的是本地开放模型。

## 我是如何实现的（How I Built It）

技术栈保持简单：原生 HTML、CSS 和 JavaScript，Python 标准库 HTTP 服务，[llama.cpp](https://github.com/ggml-org/llama.cpp)，以及采用 Q8_0 量化的 [Qwen3-0.6B-GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF)。

模型只负责一件事：根据陌生的列名和少量示例，推断每列的含义。每次请求中，每列最多发送 3 个示例值，每个值最多 100 个字符。模型不需要拿到完整商品表，就可以提出字段对应建议。

本地推理使用的输出格式约束，将每个答案限制为原表中已有的列名或 `null`，后者表示没有对应列。含义明确的 GTIN、EAN、UPC 或 barcode 列名不会被用于 SKU 建议；含义明确的 SKU 或商品编号列名不会被用于条码建议。混合含义的列名仍需要人工判断。这些约束依据的是列名含义，而不是数字长度，因为内部商品编号也可能带有前导零。

模型返回答案后，还会经过第二步校验。不存在的列名，以及与标识符类型不符的匹配，会被拒绝。如果两个字段占用了同一列，**两个字段的选择都会被清空**，应用不会按照字段排列顺序悄悄保留其中一个。

最后这条规则来自一次实际出现的错误。在演示运行中，模型把 `Kind` 同时分配给了 Product type（商品类型）和 Description（商品描述）。界面明确指出涉及的列和两个字段，解释冲突原因，并提供跳转到对应字段的检查按钮。把 `Kind` 选为商品类型，同时让商品描述保持未选择，就解决了这个冲突。模型的错误因此变成了一个用户可以看清并处理的具体选择。

只有在用户确认之后，程序才会执行确定的检查规则。价格由代码解析和比较，重复记录按完全一致的 SKU 分组，冲突值则连同所在的原始行一起列出。模型不会编造缺失的价格，也不会悄悄删除重复商品。

这样的职责划分，也让测试有了明确目标。目前的 **44 项测试**覆盖 CSV 解析、父商品记录中合法的空价格、缺失值、重复和冲突的 SKU、前导零、安全导出、字段映射校验，以及 API 错误处理。在两种推理模式下，人工确认字段后，虚构样例都能得到同样的检查报告。

Codex 协助完成了实现、测试和本文的准备。

### 处理供应商文件

应用一次接受一个 UTF-8 编码的 CSV 文件，最多 5,000 条记录、100 列，并受 2 MiB 请求大小限制。当前版本要求原表提供 SKU、商品名称和正常售价这三类列，其他字段可选。原表可以包含额外的列，但映射后的导出文件只包含所选的标准字段。

映射后的 CSV 会保留被标记的记录，供人工检查，并为后续导入做准备。价格格式使用小数点，不包含货币符号或千位分隔符。SKU 在同一文件内按完全相同的值识别，并区分大小写。

## 开放创新为什么重要（Why Does Open Innovation Matter）

供应商价格和尚未发布的商品清单可能包含敏感信息。安装好随项目提供的模型后，本地推理会把列示例留在使用者自己的电脑上，也不需要推理服务账号。这使用户能够在原本用于表格工作的硬件上反复执行检查，同时保留对数据的控制。

Qwen 的开放权重和开源推理运行程序，也让我能够查看请求内容、约束输出，并替换模型。模型发生变化时，检查规则和人工审核界面仍然可以继续使用。本地推理有硬件、电力和安装成本，但没有服务商按请求收取的推理费用。

API 模式允许用户通过兼容的服务完成推理。界面会展示发送目标，并要求用户同意将列示例发送给所选服务商。密钥只保留在页面内存中，刷新页面或点击清除设置按钮后会被清除。两种模式共用同一套字段审核和规则检查流程，用户可以选择推理运行的位置，并沿用相同的检查方式。
